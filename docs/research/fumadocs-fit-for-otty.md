# Fumadocs fit for the OTTY website relaunch

Research date: 2026-08-31

## Question

Would Fumadocs be a better fit than the selected Astro + Starlight stack for the requirements in `specs/otty-website-relaunch/spec.md`?

## Recommendation

**Keep Astro + Starlight. Fumadocs is viable, but it is not a better fit for the requirements already resolved in the specification.**

Fumadocs is not a direct static-site replacement for Astro. It is a set of documentation libraries that composes into a React framework; its current supported setup choices include Next.js and Astro with React islands. Its own documentation describes a server-first default and requires framework-specific work to produce a static build. ([Fumadocs overview](https://www.fumadocs.dev/docs/what-is-fumadocs), [static build](https://www.fumadocs.dev/docs/deploying/static), [Astro setup](https://www.fumadocs.dev/docs/manual-installation/astro))

It can deliver a custom Product Landing, prerendered Documentation, local browser-side search, filesystem navigation, Markdown/MDX, a sitemap, and a GitHub Pages artifact. The decisive issue is not feasibility. It is that Fumadocs adds React-oriented assembly while failing the specification's exact navigation-authoring contract: Fumadocs orders files alphabetically by default, but its documented override is a folder-level `meta.json` `pages` list; Starlight supports the selected per-page `sidebar.order` frontmatter with no second navigation manifest. ([Fumadocs page conventions](https://www.fumadocs.dev/docs/page-conventions), [Starlight sidebar](https://starlight.astro.build/guides/sidebar/))

Fumadocs should be reconsidered only if OTTY later needs capabilities that reward its extra flexibility, such as a deeply React-customized documentation application, multiple heterogeneous content sources, or Fumadocs-specific API-documentation tooling. None of those is in the first-launch scope.

## Spec-breaking mismatches if Fumadocs replaces Starlight unchanged

1. **Navigation ordering contract:** the spec requires alphabetical IDs by default and `sidebar.order` frontmatter as the supported override, with no duplicate navigation manifest. Fumadocs documents ordering overrides in `meta.json`, not per-page frontmatter. ([Fumadocs page conventions](https://www.fumadocs.dev/docs/page-conventions))
2. **Selected search contract:** the spec and its acceptance checks explicitly name Starlight's Pagefind output. Fumadocs static search is a different generated index and browser client, so implementation decisions 4, 36–37, 63, 67, and 69 and testing decisions 2, 5, and 12 would need coordinated revision rather than a framework substitution. ([Fumadocs built-in search](https://www.fumadocs.dev/docs/headless/search/orama), [Starlight search](https://starlight.astro.build/guides/site-search/))
3. **Static-first complexity posture:** the official Fumadocs Astro recipe wraps the docs layout and content in a `client:load` React island. That is compatible with prerendered HTML, but it is a broader hydration boundary than the selected Starlight architecture and would require fresh Lighthouse and no-JavaScript validation. ([Fumadocs Astro setup](https://www.fumadocs.dev/docs/manual-installation/astro))

These are resolvable engineering choices, not proof that Fumadocs is unsuitable in general. Resolving them would mean reopening the already resolved architecture ticket, changing the authoring and search contracts, and accepting more owned integration code. No current user story supplies a compensating benefit.

## Decision gist

Fumadocs can run fully statically and can host the OTTY landing and Documentation together, including local search. It should not replace Astro + Starlight for this relaunch because it is more assembly-heavy, its documented navigation-order override contradicts the selected frontmatter-only contract, and its static search and React hydration would require rewriting already resolved production and test seams without adding a required capability.
